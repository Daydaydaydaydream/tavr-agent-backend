# Backend 开发规划

## 1. 项目完整路线与当前步骤

以下沿用此前讨论的阶段 A / B / C 路线。当前阶段 A 的后端与 Qt 联调已由用户验证完成，下一步是阶段 B 的接口设计已完成，尚未进入 V2 实现。

| 步骤 | 阶段 / 状态 | Backend 设计与工作 | 完成标志 |
| --- | --- | --- | --- |
| 1 | A：V1 规则服务，已完成 | `/health`、`/agent/guide`、严格输入校验、无状态确定性规则 | 后端验证完成 |
| 2 | A：Qt 本机联调，已完成 | Qt 发送完整状态，后端返回 message / next_action | 用户已确认两端联调完成 |
| 3 | B：D0 接口设计，已完成设计 | 先定义真实状态、请求响应、错误码、动作、规则顺序、兼容策略及样例 | 契约审阅冻结后才写业务实现 |
| 4 | B：B1 模型实现，待开发 | 严格模型、跨字段校验、V2 错误结构，落实已冻结契约 | 模型验证与共享样例通过 |
| 5 | B：B2 规则与端点，待开发 | V2 纯规则、新端点、原因码与规则版本、能力过滤；保留 V1 | 决策表全部覆盖且 V1 行为不变 |
| 6 | B：B3 验证与交付，待执行 | 回归、日志、Qt 联调、发布依赖及回退 | 联合验收记录齐全 |
| 7 | C：知识或大模型，后续 | 独立模型适配层、超时和规则回退、结构化输出；知识来源及评估先设计 | B 阶段稳定后另立设计与验收，不允许模型绕过动作约束 |

会话存储、认证、审计、任务队列和远程部署按实际需求另行设计，尚无确定排期。测量、正式瓣环确认和报告状态须等待对应 Qt 功能完成。

日期：2026-10-14。本文为开发计划，接口基线 2.0.0 已输出，未修改业务代码。配套文档：[RCVIPlan（Qt）开发规划](rcviplan-development-plan.md)。正式协议以 [V2 接口设计](contracts/guide-v2-interface-design.md) 和 OpenAPI 为准。

## 2. 开发前置阶段 D0：先完成设计，再开始实现

本轮顺序固定为：业务语义确认 → 接口设计完成 → 契约冻结 → 两端实现 → 联调验收。Q1 和 B1 均不得在 D0 未完成时开始；不能先写状态类或接口，再由实现反推协议。

D0 设计交付已完成，采用 **2.0.0 设计基线**，不表示 V2 已实现或已运行验收。交付包括 [接口设计](contracts/guide-v2-interface-design.md)、[OpenAPI](contracts/guide-v2.openapi.yaml)、[决策表](contracts/guide-v2.decision-table.json)、[共享样例](../tests/fixtures/guide_v2/README.md) 与 [检查记录](contracts/validation-report.md)。

D0.1 业务语义、D0.2 状态字典、D0.3 HTTP 契约、D0.4 Qt 内部接口、D0.5 规则与导航、D0.6 样例均已定义；D0.7 统一版本为 2.0.0。下一步可按本设计进入 Q1 / B1。运行验收仍需实施后执行。

冻结之后任何字段、枚举、前置条件、错误码或动作语义变更，必须先更新契约和样例、记录兼容性影响，再改两端代码。V1 保持原行为。

## 3. 当前基线、目标与范围

本阶段目标是“已有规划功能的状态感知引导”：Qt 上报真实状态，后端返回与当前操作匹配的提示，用户通过明确点击进入已有界面。验收终点是能够解释等待、失败、操作回退、待保存和保存成功，而非仅证明 HTTP 通信正常。

用户已确认 V1 Qt / Backend 联调完成。本计划依据当前源码静态检查制定，未重新编译或运行 Qt。

| 项目 | 检查基线 | 当前能力 |
| --- | --- | --- |
| RCVIPlan | `b6949dc` | Qt 5、HTTP 客户端、超时和过期响应过滤、引导面板、取点页面导航 |
| Backend | `2d941e9` | FastAPI、严格请求校验、三个布尔值的确定性规则、无状态接口 |

Qt 的 `GuidanceState()` 当前只读取真实 CT 加载状态；瓣环确认和测量完成固定为 false。取点、分割和假体规划已存在，但未作为独立状态上报。`IsSentPlanReady()` 只检查点数与模型指针，不能直接代表当前规划几何有效或已保存。

历史状态文档中的 gRPC、事件订阅和旧缺陷清单不能直接当作当前需求。实施时以源码为准：同步取点、关闭保存处理和 QSaveFile 原子保存等已有实现应复用。

本期包括：状态快照、分割生命周期、取点和假体状态失效、独立保存入口、V2 规则、Qt 展示及导航、兼容和联调。

本期不新增：测量工具、正式瓣环确认、报告导出、中心线业务扩展、LLM / RAG、数据库、gRPC、事件补发、远程部署、进程内切换病例。继续采用一个进程处理一个病例、全量 HTTP 快照。

已确定：分割不新增硬前置，通过独立 alerts 提示；新增“保存定位结果”入口；只保存现有 points / rotation_matrix，明确不含假体规格；点位改变使定位失效；异步假体增加 running / failed 状态。有后台任务时正常关闭需等待任务结束。完整决策依据见正式接口设计第 2 节。

## 4. 开发前的 V2 HTTP 接口设计（已完成）

统一实现 [接口设计](contracts/guide-v2-interface-design.md) 与 [OpenAPI 3.1](contracts/guide-v2.openapi.yaml)，不再在本计划复制协议正文。新增端点 `/api/v2/agent/guide`，V1 保留。完整请求、响应、错误码、字节限制、版本关联、跨字段约束 I01–I09 和兼容策略已定义。

## 5. 当前阶段规则设计（已完成）

主规则按 CT → 保存进行中 → 点数 → 假体状态 → 保存失败/未保存/已保存排序；分割运行/失败作为独立 alerts，不覆盖主建议。主动作及告警动作分别按 supported_actions 过滤。精确规则与文案见 [决策表](contracts/guide-v2.decision-table.json)。

## 6. Backend 开发工作包

### B1：按已冻结契约实现 V2 模型（依赖 D0 已冻结）

- 新增 `app/models/schemas_v2.py`，集中定义状态、动作、原因代码和响应类型。
- 使用严格字段约束与跨字段验证；为 V2 校验错误生成精简稳定错误结构。
- 在 OpenAPI 中提供正常、运行、失败和已保存示例。
- 使用 D0 已冻结且不包含患者数据的共享 JSON 请求/响应夹具验证实现；Qt 与 Backend 必须对同一份夹具验收。以 Backend `tests/fixtures/guide_v2/` 为样例源，Qt 固定复制版本并记录来源提交，避免隐式目录依赖。新增或改变协议样例须先完成设计变更。

### B2：纯规则与新端点（依赖 B1）

- 新增 `app/services/guidance_v2.py`，同输入产生同输出，无状态、无外部调用、不修改请求对象。
- 按正式接口设计及决策表实现原因代码、文案、严重程度和动作；最后执行客户端能力过滤。
- `app/main.py` 挂载 V2 端点；如果端点和错误处理已使入口复杂，再拆 `app/routers/guide_v2.py`。
- 响应回传请求关联字段，并给出独立规则版本。
- V1 原有规则、默认值、动作和错误结构保持兼容。

### B3：测试与可排查性（依赖 B2）

- 参数化覆盖所有规则分支、优先级冲突、状态一致性约束、动作能力过滤、边界值及类型错误。
- 覆盖连续状态变化：0→1→2→3 点、删点回退、定位失效、保存失败后重试、保存后修改。
- 覆盖失败且旧结果可用、缓存命中成功、错误清除等易混淆情况。
- 保留并执行全部 V1 回归；验证异常处理器不会改变 V1 行为。
- 结构化日志只记录请求 ID、协议/规则版本、耗时、HTTP 状态、原因代码；不记录完整请求体、路径或原始进程错误。
- 更新 README、设计文档、V2 契约、联调说明和目标环境依赖冻结记录。

完成标准：V1 回归通过，V2 决策表与共享夹具通过；无需 Qt 在线或真实分割引擎即可运行后端测试。

## 7. Backend 实施顺序

1. D0 完成业务语义、接口、错误码、优先级、样例和兼容设计并冻结。
2. B1 严格按设计实现模型；实现后生成的 OpenAPI 与设计文件做一致性核对。
3. B2 实现纯规则与 V2 端点，保留 V1。
4. B3 完成自动测试与日志；与 Qt Q3/Q4 联调。
5. 后端兼容版本先部署，再切换 Qt。

Q1 与 B1 可以在 D0 冻结后独立推进；真实联调依赖 B2 与 Q3。不得把“新增 Pydantic 模型”当作接口设计阶段。

## 8. Backend 与联合验收

| 编号 | 场景 | 必须满足 |
| --- | --- | --- |
| A01 | 冷启动，有效 / 无效 CT | 首次快照准确；无效 CT 无不可执行导入按钮 |
| A02 | 0、1、2、3 个点 | 提示与真实计数一致；第 4 次取点不越界、不误增版本 |
| A03 | 创建假体后删点再补点 | 旧定位保持失效，重新定位成功后才 ready |
| A04 | 分割缓存命中 | 无需等待后台任务也能得到成功状态，清除旧错误 |
| A05 | 分割运行期间重复触发 | 不创建第二个任务；状态保持准确 |
| A06 | 配置错误、引擎失败、空结果 | 分别映射稳定错误码；不发布成功 |
| A07 | 分割结果可用但缓存保存失败 | 操作失败与结果可用同时正确表达 |
| A08 | 分割运行时关闭 | 无对象销毁后的后台访问；拒绝正常关闭并提示等待任务完成 |
| A09 | 独立保存成功 / 磁盘写入失败 | 仅实际提交成功更新保存版本；失败允许重试 |
| A10 | 保存后移动、重新取点或修改持久化参数 | 当前内容重新变成未保存 |
| A11 | 仅切页、调窗宽窗位、调显示透明度 | 不错误标记规划内容修改 |
| A12 | 状态改变后旧 HTTP 响应到达 | 成功、失败响应都不能覆盖当前提示 |
| A13 | 同状态连续刷新、响应乱序 | 只使用最新请求，关联 ID 与状态版本均正确 |
| A14 | 网络断开、超时、422、500、非 JSON、超大响应 | 可理解的错误，无导航，原业务功能可用 |
| A15 | 未知动作、缺少字段、错协议版本 | 拒绝执行；不解析中文文案作为控制逻辑 |
| A16 | 客户端不支持所需导航 | 后端返回 null，Qt 仍显示提示 |
| A17 | 用户点击导航 | 只导航或聚焦；不自动分割、取点、保存 |
| A18 | 关闭保存失败，用户取消退出 | 窗口恢复可用，引导可继续请求 |
| A19 | 新 Backend + 旧 Qt | V1 行为与已验证版本一致 |
| A20 | V2 Qt + 仅 V1 Backend | 明确版本不匹配；显式切回 V1 后可运行 |
| A21 | 非法枚举、布尔字符串、超界点数、矛盾版本 | V2 返回稳定 422，不回显原始输入 |
| A22 | 当前版本保存成功且仍有效 | 仅显示“当前取点与定位矩阵已保存（不含假体规格）”，不声称测量或完整流程完成 |

每条记录至少包含：两端提交号、环境、输入/操作、预期、实际、通过/失败、必要截图或日志。未运行的场景标为未执行，不能用静态检查代替。

后端自动验证覆盖 HTTP 约束及全部规则；涉及 Qt 窗口、线程、保存和导航的场景由 Qt 执行，两端共同核对结果。补充验证 415、422/500 错误结构、error.details 上限、request_id 无法解析、响应字段长度和 V1 异常结构兼容。

## 9. 发布与回退

1. 保留 V1 已通过验收的提交标识和运行配置。
2. 部署支持 V1 + V2 的 Backend，先用夹具验证 V2，再用旧 Qt 回归 V1。
3. 发布支持显式协议选择的 Qt，在测试环境启用 V2 完成 A01–A22。
4. 目标环境验证依赖后冻结版本；不直接把开发机全量环境当作发布依赖。
5. 引导出现问题时先将 Qt 显式切回 V1；V1 的两个未实现完成标志仍保持 false。
6. Qt 若修改保存格式，必须先验证旧版读取兼容性。协议切回 V1 不等于文件格式回退，不得靠回退程序覆盖新版文件。

## 10. 后续阶段 C：知识或大模型的设计顺序

先明确受支持问题和知识来源、版本、评估样本；再定义解释/问答接口、模型适配层、超时、取消与失败回退，最后实施。确定性规则继续约束动作范围，模型不能任意调用桌面功能。模型输入范围和数据边界应在设计中明确；LLM、检索、存储及部署均不纳入本轮 B 阶段实现。
